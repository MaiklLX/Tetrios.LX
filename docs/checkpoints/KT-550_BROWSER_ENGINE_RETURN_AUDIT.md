## Решение по архитектуре

Block Buddies возвращается к существующему браузерному runtime. Основное игровое поле, логика фигур, столкновения, таймеры, режимы и сенсорный ввод остаются в HTML/JavaScript и 2D Canvas. Godot не становится новым runtime и не переносится в браузер.

Сохраняем:
- старый браузерный запуск без обязательного Godot/WebAssembly runtime;
- 2D-поле 10×23 и существующую игровую механику;
- Golden Desktop Baseline #372;
- текущие режимы, прогресс, сохранения, героев, кампанию и награды;
- возможность упаковать тот же web runtime в Android WebView APK.

Godot KT-549 остаётся отдельной веткой/референсом. PR #84 остаётся Draft и не объединяется. Его идеи переносим по одной, адаптируя под существующие DOM/CSS/Canvas-компоненты, а не копируя Godot-код.

## Что обнаружено в браузерной базе

1. `site/index.html` содержит действующий браузерный игровой runtime и обработчики `touchstart/touchmove` на Canvas. Сенсорные жесты уже обрабатываются в игре; задача — точечно улучшить распознавание, не заменить систему ввода.
2. Кампания имеет каталог на 360 узлов. `bbGetNodeInfo` определяет биом, локальный номер, босс-узлы и финального босса; `bbGetNodeGoals` формирует цели миссии. Сначала улучшаем представление существующей кампании, не создаём вторую систему прогрессии.
3. Уже существуют наградные окна, сундуки реликвий, фрагменты коллекции и обмен фрагментов. Новую ленту наград нужно встроить в текущую коллекцию/экран наград и сохранить старые ключи сохранения.
4. Уже есть тренировка героев (`bbCampaignTraining`), но это не равно первому обучающему туру по меню и управлению. Обучение новичка нужно проектировать отдельно, с пропуском и сохранением завершения.
5. В HTML уже присутствуют визуальные модули `hero-arena.js`, `visual-3d.js` и `universes-3d.js`. Они не должны становиться обязательной зависимостью игрового цикла. Проверяем их влияние на производительность и возможность оставить их как декоративные/опциональные слои, сохранив 2D Canvas источником истины.
6. APK pipeline уже существует: `.github/workflows/build-apk.yml`, `.github/workflows/release-apk.yml`, Android WebView project ZIP и скрипт синхронизации web assets. Ничего не запускаем и не публикуем в рамках этого аудита.

## Порядок работ и критерии приёмки

- **KT-551 — управление:** жест начинается только на свободной игровой поверхности; явные кнопки не перехватываются; диагональный жест не превращается в вращение; hard-drop не блокирует последующие лево/право/вращение; soft-drop остаётся доступен.
- **KT-552 — арена:** поле 10×23 максимально использует безопасную область экрана; HUD, Hold/Next, цели и DROP не перекрываются; desktop #372 не регрессирует.
- **KT-553 — отклик/HUD:** нажатие заметно на touch и мыши; значения и подписи читаемы; управление и игровые события не меняются.
- **KT-554 — награды:** лента прокручивается горизонтально, выбранная карточка видна, карточки крупнее; старые коллекционные ID, фрагменты, валюты и сохранения остаются совместимыми.
- **KT-555 — карта:** вертикальное восхождение читаемо снизу вверх, текущий прогресс виден, боссы отмечены, верхняя точка — финальная; логика 360 узлов и открытий не переписывается.
- **KT-556 — onboarding:** показывается один раз, можно пропустить, завершение сохраняется; обучающий слой не блокирует игровые кнопки и не ломает существующую тренировку героев.
- **KT-557 — регрессия:** повторно использовать существующие `scripts/cross-platform-visual-preview.cjs` и workflows Chromium/WebKit; проверить desktop, мобильный portrait/landscape, все режимы, кампанию, сохранения и консоль. APK workflow только проверить статически/на тестовой ветке после отдельного согласования.
