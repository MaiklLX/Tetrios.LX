# KT-446 — Web → Godot save audit and migration contract

- Date: 2026-11-08
- Read-only source baseline: `main` at `38c61b606187b88ce8a48a1c6b71d264aecf4258` (`site/index.html`).
- Target: `godot/kt428-buddy-companion-2026-11-07`, Draft PR #77.
- Status: **AUDIT COMPLETE / CONTRACT PROPOSED / IMPLEMENTATION NOT STARTED**.
- Safety: no writes to `main`, no deployment, no data reset, no APK build.

## 1. Executive result

The current Web build does not have one canonical save document. It has a collection of localStorage keys written by several subsystems. Some values are duplicated under legacy aliases, some are date-indexed, and some are run-local and intentionally recreated at each run.

A blind key copy is unsafe. The Godot implementation should use a versioned native profile document with explicit sections and a separate in-progress run snapshot. Migration must be read-only until a complete export/backup and validation path exists.

The current Godot `to_save_data()` / `load_save_data()` pair is an **in-memory run snapshot only**. It is not connected to disk, user:// storage, autosave, profile progression, or Web import.

### Key-prefix clarification

- `bbGet(k)` reads the actual key `bb_${k}`; `bbPut(k,v)` writes JSON to that same key.
- Therefore `bbPut('bbCampaignPerks_'+heroId,...)` produces `bb_bbCampaignPerks_<heroId>`, not `bbCampaignPerks_<heroId>`.
- Direct keys such as `bbCampaignMarks`, `bbSelectedHero`, `bbDailyQuests`, `bbCoins`, and `nrRelics` do not use the helper.
- The source contains both raw aliases and helper-managed keys. Treating every key beginning with `bb_` as an identical data type would corrupt values.

## 3. Data that is currently run-local, not durable profile progress

The inspected source initializes these when a run starts or rebuilds them during play:

- Active board, current/next pieces, score/lines/level/time, pause/game-over state.
- `bbCampaignRun` objective counters and `bbNodeCompleted`.
- Block Run room/encounter state, enemy HP/attack countdown, run goals, selected upgrade cards/ranks, shield/reserve charges and active boosts.
- Daily modifier runtime state and replay payment flags.
- Current campaign node selection/arrival animation state.

These should not be mistaken for saved profile progression. The Godot run snapshot can eventually persist an interrupted run, but it must remain a separate document from the durable profile. Mode-specific snapshots require their own schema and validation before they are enabled.

## 4. Alias and consistency hazards

1. **Coins have three browser keys.** The helper-managed `bb_coins` is loaded into the live wallet and is written by `bbSave()`. Direct reward code also writes `coins` and/or `bbCoins`, but not every path updates all three at once. Migration must not sum these values. It needs a documented precedence rule and conflict report; if values disagree materially, preserve all raw values in a backup and require a deterministic reconciliation rule.
2. **Captain Plush has legacy XP aliases.** `bb_xp` and `bb_heroLevel` mirror `bb_xp_plush` and `bb_heroLevel_plush` on several paths. Import should prefer valid per-hero values, fall back to the legacy aliases only when per-hero fields are absent, and retain the original payload in backup.
3. **Cosmetic equip has a legacy single-slot key.** `bb_equippedChestCosmetic` is converted to a per-hero object for the currently selected hero. Import should preserve this fallback behavior without deleting the source key.
4. **Daily completion is represented in several places.** The completion date, per-date reward marker, history record, and replay array have overlapping but non-identical meanings. Do not infer a reward solely from one field or grant it again during migration.
5. **Campaign and relic currencies are separate.** `bbCampaignMarks` and `nrRelics` are different wallets with different sinks. Never merge them.
6. **Storage writes are not uniformly guarded.** Some direct `localStorage.setItem` calls and `bbPut` have no exception recovery. Native save writes must be atomic and preserve the previous valid file on failure.

## 5. Reset-flow warning

The source has two reset handlers. They remove the `bb_` prefix family and a hard-coded list, but the list does not explicitly include every direct daily key or dynamic `bbDailyRewardClaimed:<date>` key. The reset flow is not a reliable migration inventory and must not be reused as one.

This audit did not execute the reset flow and did not modify any user data.

## 6. Proposed Godot save contract (not yet implemented)

Use two independent versioned documents under Godot `user://`:

### Profile document — durable progression

```json
{
  "schema_version": 1,
  "profile": {
    "created_at": "",
    "updated_at": "",
    "source": "godot"
  },
  "economy": {
    "coins": 0,
    "gems": 0,
    "relics": 0
  },
  "campaign": {
    "unlocked_node": 1,
    "marks": 0,
    "hero_perks": {}
  },
  "heroes": {
    "selected_id": "plush",
    "progress": {},
    "active_skill_state": {}
  },
  "inventory": {
    "consumables": {},
    "permanent_perks": []
  },
  "cosmetics": {
    "owned": [],
    "equipped_by_hero": {},
    "fragments": 0
  },
  "daily": {
    "quests_current": {},
    "quest_archive": {},
    "challenge_catalog_signature": "",
    "challenge_assignments": {},
    "challenge_history": {},
    "last_completed_date": "",
    "replayed_dates": [],
    "reward_claimed_dates": [],
    "visit_streak": {}
  },
  "stats": {
    "best_score": 0,
    "runs": 0,
    "last_daily_run_date": ""
  },
  "settings": {
    "haptics": true
  },
  "migration": {
    "source": "web_localstorage",
    "source_schema": "legacy-unversioned",
    "completed": false
  }
}
```

This is a **shape proposal**, not a finalized list of game rules. Fields such as active-skill state need a separate parity audit before implementation.

### Run document — resumable session

- `schema_version` independent from the profile version.
- `mode_id` and mode-specific payload.
- Core board snapshot from KT-445.
- Timer/pause state and any mode state only after that mode's rules are ported and tested.
- A run snapshot must never overwrite profile wallets or rewards.
- Reward settlement must be idempotent and occur once, after validated completion.

### Atomic write and recovery requirements

1. Validate a complete candidate document before touching the current save.
2. Write to a temporary file, flush/close, then replace the active file; retain a last-known-good backup.
3. On invalid/unknown schema, do not partially load and do not auto-reset. Keep the original file and surface a recoverable error.
4. Keep migration source payload/backup until the user has launched and validated the migrated profile successfully.
5. Migration must be one-way and idempotent: repeating it must not duplicate currency, rewards, inventory or completion markers.
6. No cloud sync/account merge is assumed; no external service contract was found in this source audit.

## 7. Web → Godot migration precedence (proposed)

- Parse all recognized source keys into a read-only candidate first.
- Keep exact raw key/value pairs in a backup manifest; unknown keys remain untouched and are reported, not discarded.
- Coins: prefer `bb_coins` as the live wallet source because it is the value loaded by the current Web runtime; record `coins` and `bbCoins` as aliases and detect conflicts. This precedence still requires a dedicated compatibility fixture against the latest deployed Web behavior before implementation.
- Plush progression: prefer per-hero `bb_xp_plush` / `bb_heroLevel_plush`; use `bb_xp` / `bb_heroLevel` only as fallback.
- Other heroes: read per-hero keys only; absent heroes start at their defined defaults.
- Campaign: `nrNode` and `bbCampaignMarks` remain separate.
- Block Run: `nrRelics` remains separate from campaign marks.
- Cosmetics: use `bb_equippedChestCosmetics`; fallback to `bb_equippedChestCosmetic` only if the map is absent/invalid.
- Daily rewards: import all markers/history exactly; never issue rewards during import.
- Daily quest archive: preserve existing dates and entries; do not regenerate old dates from today's catalog.
- Haptics and score/run stats are non-economy fields and must not be allowed to overwrite progression on a partial import.

## 8. Required fixtures before persistent storage is enabled

1. Empty Web profile with defaults.
2. Typical profile with all five heroes, inventory, perks, cosmetics, campaign node and both currencies.
3. Coin alias agreement and all known disagreement permutations.
4. Plush legacy XP only; Plush per-hero only; both present with matching values; both present but conflicting.
5. Legacy single cosmetic equip; per-hero cosmetic equip; invalid owner collision.
6. Daily quest current date, stale date, 90+ day archive trim, challenge catalog signature change.
7. Standard daily completion with marker/history/date all present; full dated challenge assignment/history snapshots; `completed` versus `replayed` status; partial marker combinations; valid, invalid and duplicate replay dates; already replayed date.
8. Unknown Web key preservation and malformed JSON handling.
9. Unknown/future native schema rejection without overwriting the prior valid file.
10. Interrupted atomic write recovery and backup restore.
11. Repeated import idempotency: balances and reward markers unchanged after the second pass.
12. Round-trip profile + separate in-progress run without cross-contamination.
