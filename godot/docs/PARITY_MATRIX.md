## 3. Confirmed campaign and Block Run systems

- Campaign run counters include maximum clear, pieces placed, rotations, Hold uses, hard drops, single/double/triple/Tetris clears, and maximum combo. Source: `bbCampaignRun` initialization in `startGameNow()`.
- Campaign node goals include tactical/skill objectives such as rotations, Hold, double clears, no hard drop, and streak; the exact node goal table is in `bbGetNodeGoals(node)`.
- Block Run starts with a room/floor encounter. Boss is every fifth room; encounter HP and attack countdown are calculated in `bbRogueStartRoom()`.
- Block Run has three run goals generated by `bbCreateRogueGoal()`.
- The upgrade catalog has 35 entries. Checkpoint #389 records four Block Run-only IDs (`burst`, `rift`, `reserve`, `hunter`) and 31 shared catalog entries; actual rank/draft application is gated to Block Run.
- Monster attack profile, attack-row construction, telegraph countdown, reserve counter, and damage resolution are implemented in `bbRogueGetAttackProfile()`, `bbRogueBuildGarbageRow()`, `bbRogueEnemyAttack()`, and `bbRogueDamageEnemy()`. Do not substitute a generic attack without preserving these rules.

## 5. Hero progression and abilities

- Hero XP and levels are stored per hero using `xp_<heroId>` and `heroLevel_<heroId>`; legacy aliases `xp` and `heroLevel` exist for Captain Plush.
- Active abilities unlock at hero level 5 and use a 45-second cooldown (`bbUseHeroActiveSkill()`, `bbRenderHeroSkillSlot()`).
- Ability behavior differs between Block Run and non-rogue modes. The exact five hero branches are in `bbUseHeroActiveSkill()`; preserve both branches rather than flattening them.
- Campaign perks are per hero under `bbCampaignPerks_<heroId>`; they are campaign-only (`bbHasCampaignPerk()`).

## 6. Persistence fields observed in source

The web implementation persists data in browser localStorage via `bbPut()`, `bbGet()`, `bbSave()` and direct localStorage calls. Confirmed key families include:

- Economy/progression: `coins`, `gems`, `xp`, `heroLevel`, `xp_<heroId>`, `heroLevel_<heroId>`, `bbCampaignMarks`, `nrNode`, `nrRelics`.
- Hero/loadout/cosmetics: `bbSelectedHero`, `bbCampaignPerks_<heroId>`, `equippedChestCosmetics`, `bb_equippedChestCosmetic`, `chestCosmetics`, `collectionFragments`.
- Inventory and perks: `inventory`, `perks`.
- Daily challenges: `bbDailyChallengeCatalogSignature`, `bbDailyChallengeAssignments`, `bbDailyChallengeHistory`, `bbDailyChallengeCompletedDate`, `bbDailyArchive`, `bbDailyReplayCompleted`, `bbDailyRewardClaimed:<date>`, `bbDailyQuests`.
- Visit streak and related state: `bbVisitStreak`, `bbCampaignMarks`.

This is an inventory of observed keys, not a finalized native save schema. Before implementing persistence, audit every `bbPut()` and `bbGet()` call, define versioned schema/migrations, and distinguish durable account-like progress from run-local state. Do not copy localStorage blindly.

## 7. Deterministic fixtures required before gameplay port

1. Board: empty 10×23 grid; spawn at each edge; top-out; collision against walls/floor/locked cells.
2. Seven-bag/randomizer: capture deterministic sequence and bag-boundary behavior from source `randomType()`.
3. Rotation: each piece in open space, against both walls, on floor, and adjacent to locked cells; exact accepted kick offset.
4. Drop/hold: soft-drop score, hard-drop distance score, hold once/twice where hero/card rules permit, hold swap and reset behavior.
5. Clears: 1/2/3/4-line clear; exact score, levelLines, lines, level, next gravity delay; multiple adjacent rows.
6. Campaign: each goal type, contradictory goal exclusion, completion gate, campaign perk effect.
7. Block Run: room 1, room 5 boss, room/floor transition, attack warning at threshold, attack resolution, reserve absorption, monster defeat, each card rank/synergy.
8. Daily: fixed date assignment, catalog signature change, completion, replay price, each modifier family, reward idempotency.
9. Heroes: all five active abilities in both rogue and non-rogue contexts; level 4/5 boundary; cooldown boundary; XP thresholds.
10. Persistence: fresh profile, returning profile, partially completed daily, campaign node, hero levels, inventory/cosmetics; malformed or older save migration.

## 10. Detailed save audit addendum — KT-446

The full key inventory, sampled data shapes, actual helper-expanded key names, alias/conflict hazards, reset-flow warning, proposed native profile/run split, migration precedence, atomic-write requirements and required migration fixtures are documented in [SAVE_MIGRATION_CONTRACT.md](SAVE_MIGRATION_CONTRACT.md).

Important corrections/clarifications from the deeper source pass:
- `bbGet('coins')` / `bbPut('coins', ...)` operate on actual key `bb_coins`; `coins` and `bbCoins` are separate raw aliases/mirrors and are not consistently synchronized by every reward path.
- Per-hero campaign perks are stored under actual keys `bb_bbCampaignPerks_<heroId>` because the helper adds its own `bb_` prefix.
- Campaign marks (`bbCampaignMarks`) and Block Run relics (`nrRelics`) are separate currencies.
- Current daily quests, quest archive, challenge assignment/history/completion/replay markers and visit streak are separate records; importing them must never issue rewards.
- KT-445 currently serializes an in-memory gameplay run only. It does not implement disk persistence or the durable profile described in the new contract.

Status: **KT-446 source audit and proposed contract complete; implementation and migration fixtures pending.** No Web source, main branch, deployment, APK or user data was changed.
